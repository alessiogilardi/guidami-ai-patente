# Patterns and Conventions

Enforceable rules (typing, DI ordering, config-loading, import style) live
in `~/.claude/rules/python/` and `.claude/rules/`. This file only records
recurring idioms actually adopted in the code, as a reference for reuse —
it does not restate those rules.

## Adopted patterns

| Pattern | Where it's used | Why |
|---|---|---|
| `UseCase[T_In, T_Out]` / `AsyncUseCase` protocol | `src/commons/use_cases/use_case.py` — `__call__` is `@final`, delegates to abstract `execute()` | Uniform callable contract for domain logic; every business-logic unit is typed, testable, composable |
| `ForEach[T, U]` | `src/commons/use_cases/for_each.py` — a `UseCase[Iterable[T], list[U]]` wrapping a per-item callable | Turns any `UseCase`/callable into a list-mapper without per-step loop boilerplate |
| `FlatMap[T, U]` | `src/commons/use_cases/flat_map.py` — a `UseCase[Iterable[T], list[U]]` wrapping a per-item `Callable[[T], Iterable[U]]`, concatenating results | One-to-many transforms (one input produces N outputs); e.g. `ApplyStep("expand_to_embeddable_commas", FlatMap(ArticleMapper.from_cleaned_to_embeddable_commas), ...)` in `orchestrators/knowledge_flows.py` (a plain `@staticmethod` reference works directly, no callable-instance wrapper needed — `FlatMap.__init__` only requires `Callable[[T], Iterable[U]]`) and `ApplyStep("flatten_quiz", FlatMap(QuizMapper.from_parsed_to_cleaned_all), DeduplicateQuizItems(), ...)` in `orchestrators/quiz_flows.py`. A third shape, zero-or-one rather than one-to-many: `ApplyStep("map_to_quiz_images", FlatMap(QuizMapper.from_embedded_to_quiz_images), ...)` (spec 0008 Phase 1) returns `[QuizImageEntity]` when the question has an image, `[]` otherwise — `FlatMap` needs no dedicated zero-or-one variant, since a `Callable[[T], Iterable[U]]` already covers the empty-list case for free |
| `ApplyStep(ForEach(...))` composition | `orchestrators/knowledge_flows.py` — e.g. `ApplyStep("map_to_chunk_entity", ForEach(ArticleMapper.from_embeddable_chunk_to_knowledge_chunk), ...)` | Standard glue between the domain-agnostic `flowstep` framework (external git dependency, see `docs/architecture.md`) and per-item domain transforms/mappers |
| `AsyncApplyStep` | `flowstep.steps` (external git dependency, same package as `ApplyStep`) — used in `orchestrators/quiz_flows.py::build_quiz_enrichment_flow` for the LLM-enrichment step (knowledge-corpus enrichment used it too, until spec 0001/T-13 removed that flow entirely) | Fully generic (owns one `asyncio.run`, no repo-specific coupling), so it belongs upstream per the `flowstep`-vs-local split documented in `docs/layout.md`; no local copy is kept |
| `Iterable[T]`-typed `ApplyStep` transforms | All `UseCase` subclasses passed as `ApplyStep(...)` transforms (`ForEach`, `FlatMap`, `DeduplicateQuizItems`, `EmbedQuizMetadata`, `ImageDescriptionEnricher`, `NormReferenceEnricher`) declare `execute(self, request: Iterable[T]) -> list[U]` | `flowstep`'s `ApplyStep` (external dependency) types transforms as `Callable[[Iterable[Any]], Iterable[Any]]`; a `list[T]`-only parameter fails pyright. Transforms that traverse `request` more than once materialize it first (`request = list(request)`) since `Iterable` doesn't guarantee re-iterability |
| Dedup-before-LLM enricher via `deduplicate` | `services/quiz/enrichers/norm_reference_enricher.py` — build a `dict[key, response]` by mapping `commons.utils.deduplicate(items, key=_make_key)` through the agent, then broadcast each response to every row sharing the key | One LLM call per unique key instead of per row; the order-preserving `deduplicate` pass replaces manual `seen`-set bookkeeping |
| Group-by-resource enricher with concurrent LLM calls | `services/quiz/enrichers/image_description_enricher.py` — `_group_by_image` (sync `defaultdict(list)`, keyed on the image filename only) → `_fetch_descriptions` (async: builds every `RoadSignDescriberRequest` first via `RoadSignDescriberMapper.from_enriched_quizzes_to_request` — one per image, concatenating every quiz's context — then fires `_describe_image` calls with `asyncio.gather` under an `asyncio.Semaphore(max_concurrency)` created per run) → `_enrich_quiz` (sync, broadcasts each response to every quiz sharing that image). `execute` stays sync and drives the async part with `asyncio.run(...)` | One vision call per **image**, not per `(image, topic, text)` triple — the describer is answer-blind and already treats quiz text as weak context, so per-triple specialization only bought divergent/costlier calls. The semaphore is built fresh per `_fetch_descriptions` call (never stored on `self`) because an `asyncio.Semaphore` binds to the event loop of its first use, and `execute`'s `asyncio.run` spins a fresh loop every call — storing it would break re-use across runs. Per-image failures degrade (`None`, logged) without aborting the batch |
| `embedded_text` computed property | `models/knowledge/embeddable_article_comma.py::EmbeddableArticleComma` (`"\n".join(p for p in (self.article_title, self.text) if p)` — title + comma text only, no context, since T-13 removed LLM enrichment entirely per AD-18); on the quiz side it lives on `models/quiz/quiz_metadata.py:QuizMetadata` directly — `EmbeddedQuizModel` no longer needs it, since `EmbedQuizMetadata` embeds `quiz_metadata` (itself `Embeddable`) rather than the wrapping model | Single source of truth for "what text gets embedded", decoupled from the persisted entity's fields |
| Structured field + `@computed_field` render/translate | `agents/dto/road_sign_describer/road_sign_describer_request.py` — `contexts: list[QuizContextModel]` (`QuizContextModel`: `topic: str`, `texts: list[str]`) stays the structured DTO field, one entry per distinct topic; `contexts_block` (`@computed_field @property`) renders it into an `Argomento: <topic>\nDomande:\n- <text>` block per topic (blocks joined by a blank line) that the prompt template substitutes. `agents/dto/norm_reference_describer/norm_reference_describer_request.py` — `correct_answer: bool` stays typed; `correct_answer_it` (`@computed_field @property`) renders it as the Italian `"Vero"`/`"Falso"` literal the prompt template substitutes | `PromptRenderer` does `model_dump()` + `Template.safe_substitute`, and `model_dump()` includes computed fields — so the template references the derived field (`$contexts_block`, `$correct_answer_it`) while the request DTO itself keeps the structured/typed field, never a pre-rendered prompt string. Confirmed repeated pattern (two independent DTOs) for any request field needing a prompt-specific rendering (list → text block, bool → Italian literal, etc.) — a third instance (`article_contextualizer_request.py`'s `paragraphs_block`) existed until spec 0001/T-13 removed knowledge-corpus enrichment entirely. `RoadSignDescriberMapper._from_enriched_quizzes_to_quiz_context` groups deduplicated `(topic, text)` pairs into one `QuizContextModel` per topic so multiple quiz texts under the same topic render as one `Domande:` bullet list instead of repeating the topic heading; it also deduplicates quiz text globally across topics (a `seen_texts: set[str]`, first-seen topic wins) so a literal text repeated under a different topic isn't rendered twice |
| `embed_repealed` config flag | `configs/ingestor_config.py` (default `False`), consumed by `orchestrators/steps/knowledge/embed_commas_step.py::EmbedCommasStep` | Lets repealed norms be indexed or excluded without a schema/pipeline change |
| Per-element layer I/O + element-derived stable id | `commons/utils/element_id.py` (`element_id(*parts) -> str`, a `uuid5` over a fixed, non-configurable namespace) + `orchestrators/steps/generic/{load_json_dir_step,filter_already_done_step,write_json_dir_step}.py` + `LayerResolver.dir(layer, source)` (container directory, stops before `SourceConfig.file`) + `repositories/file_repository/_base_file_repository.py::load_dir(dir)` + `clients/file_system/*::list_files` | Knowledge's `cleaned` layer is one-JSON-file-per-article, keyed by `element_id(article.source, article.number)` (`orchestrators/knowledge_flows.py::_article_id`) instead of one monolithic file per source. `specs/0006-quiz-per-element-layers.md` applied the identical pattern to quiz's `cleaned`/`enriched` layers, keyed by `element_id("quiz", item.number)` (`orchestrators/quiz_flows.py::_quiz_id`) — quiz has a single fixed source, so (unlike knowledge, which had to add a `source` field to `CleanedArticleModel`) no new model field was needed, `number` alone is already the stable natural key. `FilterAlreadyDoneStep` (parametrized by an injected `id_of: Callable[[T], str]` keyer, not a domain-aware class) drops elements whose destination file already exists, giving cross-run resumability (`--force` bypasses it) without any write-through/async rework — that is deferred to a follow-up plan. In quiz's enrichment flow specifically, the filter runs *before* the cleaned→enriched mapping/LLM step (cost-driven placement, since that transform — not a cheap in-memory map — is the expensive part); in both cleaning flows the filter instead runs *after* the transform that produces the element's id, since the id is only computable post-transform (structural placement). All three steps are domain-agnostic, mirroring `LoadJsonStep`/`WriteJsonStep`'s existing split for monolithic layers (still used for both entities' single-file `parsed` layer, and by quiz's own former monolithic `cleaned`/`enriched` files before spec 0006); granularity (monolithic vs per-element) is decided by which steps a flow's builder wires in, not by a config flag |
| `FileRepository[T]` protocol as the DI type for generic I/O steps | All four `orchestrators/steps/generic/{load_json_step,write_json_step,load_json_dir_step,write_json_dir_step}.py` type their `repository` constructor param as `repositories/file_repository/file_repository_protocol.py::FileRepository[T]` (not the concrete `JsonRepository[T]`); the protocol declares five shape-specific methods — `load_one`/`load_list`/`load_dir`/`write_one`/`write_list` — matching exactly what `BaseFileRepository` subclasses (`JsonRepository`, `YamlRepository`) provide, and each step calls exactly one of them (`LoadJsonStep`→`load_list`, `LoadJsonDirStep`→`load_dir`, `WriteJsonStep`→`write_list`, `WriteJsonDirStep`→`write_one`) | DIP: each step only ever calls its one method, so depending on the protocol instead of a concrete format class makes them genuinely format-agnostic (a `YamlRepository[T]` can be injected with no code change) and gives the previously-unused, already-defined `FileRepository` protocol an actual purpose. The five methods replaced an earlier `load`/`write` pair typed `T \| Sequence[T]` plus `load_dir`'s predecessor `load_all` — rule (with rationale) in `.claude/rules/code-conventions.md`, "Shape-polymorphic APIs — one method per shape", not restated here. Everything stays on the one `FileRepository` protocol rather than splitting into a file-protocol and a dir-protocol, because both current implementers provide all five for free via the shared `BaseFileRepository` base, and the protocol is scoped to file/directory persistence, not a generic multi-backend `Repository` |
| `BaseAgent[T_In, T_Out]` + `PromptRenderer` | `src/commons/ai/agents/base_agent.py` (wraps `pydantic_ai.Agent`, `from_yaml` factory returning `Self`, `run`/`run_sync`/`__call__`); concrete agents declare `output_type` as a class attribute (e.g. `output_type = RoadSignDescriberResponse`) and inherit `from_yaml` unchanged — no override, no `# type: ignore` | Shared LLM plumbing (config load, prompt rendering, retries); per-agent code reduces to the generic params, the `output_type` attribute, and a prompt file |
| Structured per-call logging via a shared completion helper | `base_agent.py::BaseAgent._log_call_completed(capture)`, called from both `run`/`run_sync` after the tracked `with` block — reads `capture.log` (the `LlmCallLogEntity`) once into a local, logs `info` with `latency_ms`/input-output-total tokens/`cost_usd`, then `warning`s if `cost_usd` is `None` (OpenRouter reported none). The pre-dispatch `debug` log includes image count and prompt char length | `.claude/rules/logging.md` "Reference implementation"; avoids rebuilding the entity per logged field, and surfaces a previously-silent missing-cost case as an explicit degraded-condition warning instead of a silently-null DB column |
| Repository with scoped upsert + reconciliation (`*StoreRepository`) | `repositories/db/{article_store_repository,article_comma_store_repository}.py` (spec 0001 T-10; superseded `knowledge_chunk_store_repository.py`, deleted T-15; upsert path spec 0010 T-1/T-2/T-3) extend `UpsertStoreRepository[ArticleEntity]`/`[ArticleCommaEntity]` (renamed from `BulkInsertStoreRepository`), add `delete_missing` alongside the inherited `truncate`/`upsert`/`upsert_returning_ids`. `ArticleStoreRepository.delete_missing(source, present)` deletes rows of that `source` whose `number` is absent from `present`; `ArticleCommaStoreRepository.delete_missing(article_ids, present)` deletes commas of those `article_ids` whose `(article_id, comma_number)` is absent from `present`, via an `unnest(...)` + `NOT EXISTS` anti-join, not a subquery on `articles.source` (`article_commas` has no `source` column of its own). `StoreArticlesAndCommasStep` calls `ArticleStoreRepository.delete_missing` only — a reconciled-away article's commas go by `article_commas.article_id`'s `ON DELETE CASCADE` (see `docs/database.md`) — then calls `ArticleCommaStoreRepository.delete_missing` to catch commas whose parent survived but whose own key did not; `delete_source` (both classes) is gone, superseded by this pair. No `%s::vector` cast needed on `embedding` for a plain `INSERT`/upsert — `PostgresClient` registers the pgvector adapter connection-wide; the cast rule in `.claude/rules/code-conventions.md` only applies to the `<=>` operator context. Quiz side (spec 0008 Phase 1): `QuizQuestionStoreRepository` gained the same `UpsertStoreRepository` + `delete_missing` shape, replacing its former `DbStoreStep`-driven truncate + bulk-insert path, but with **no `source` parameter** — quiz has a single source, so `delete_missing(present)` scopes the whole table (`repositories/db/quiz_question_store_repository.py`). New `QuizImageStoreRepository` (`repositories/db/quiz_image_store_repository.py`) extends `UpsertStoreRepository[QuizImageEntity]` with **no** `delete_missing` at all — reconciling orphaned images (a description no question references anymore) is an explicitly deferred open question, not an oversight. `StoreQuizStep` (`orchestrators/steps/quiz/store_quiz_step.py`) is the quiz-side counterpart of `StoreArticlesAndCommasStep`, calling both repositories; the generic `DbStoreStep`/`StoreRepository` protocol it replaced are deleted (AD-10), zero remaining callers | Upsert on the natural key keeps a row's `id` stable across runs, so child rows keep referencing it; the reconciling delete, scoped to what the run owns, preserves the old truncate-and-reinsert mirror semantics without ever issuing a `TRUNCATE` (spec 0010, AD-1/AD-2; extended to quiz by spec 0008 Phase 1) |
| Bulk insert returning generated ids (`bulk_insert_returning_ids`) | `ArticleStoreRepository.bulk_insert_returning_ids(items: list[ArticleEntity]) -> list[int]` (spec 0001 T-10) — builds `INSERT ... RETURNING id`, calls `PostgresClient.execute_many_returning`, returns one id per input item **in input order** | `article_commas` rows must FK-reference their parent `articles` row's DB-generated `id`; `StoreArticlesAndCommasStep.execute` zips the returned id list against the input articles' `number`s into an `article_id_by_number: dict[str, int]`, then `ArticleMapper.from_embeddable_comma_to_article_comma(comma, article_id_by_number)` resolves each comma's FK via that `number`-keyed lookup |
| Static, verbose mapper methods (`from_X_to_Y`) | `mappers/article_mapper.py`, `mappers/quiz_mapper.py` — all methods static and pure, one pure function per pipeline-stage transform | Confirmed convention: mappers are static utility classes, never DI-injected (see also `feedback_mappers_static_verbose` memory). When a mapper class has only **one** method, the generic `from_model_to_entity` name is used instead of naming the concrete types (e.g. `commons/ai/observability/mappers/llm_call_log_mapper.py`) — no ambiguity to resolve with a single method; multi-method mappers (`ArticleMapper`, `QuizMapper`) keep the specific `from_X_to_Y` style to disambiguate between methods |
| Entity = insertable row projection | `domain/entities/knowledge/{article,article_comma}.py`, `domain/entities/quiz/quiz_question.py` — DB-generated columns (`id`, `created_at`) have **no** field on the entity; `QuizQuestionEntity`'s docstring states the omission; `ArticleCommaEntity.article_id` **is** included since it's a caller-supplied FK, not DB-generated | Rule (with rationale) in `.claude/rules/code-conventions.md`, "Entities — insertable projection of the table row" — not restated here. Entities are persistence DTOs by design; rich DDD entities deferred until the FastAPI app brings real invariants |
| Italian prompt-facing text on agent response DTOs | Every `agents/dto/*/*_response.py` (`NormReferenceDescriberResponse`, `RoadSignDescriberResponse`) — class docstring + every `Field(description=...)` are in Italian; an inline note on each class explains why | Rule (with rationale) in `.claude/rules/code-conventions.md`, "Exception — prompt-facing text on agent response DTOs" — not restated here. `pydantic_ai.Agent(output_type=...)` ships this text to the LLM as the JSON schema, so it's prompt content, not code documentation; request DTOs (`*_request.py`) stay English since their docstrings are never shipped as schema |
| Config loaded once at entry point | `cli/main.py` — `IngestorConfig()` constructed inside `main()`, then passed down into every `build_*_flow(config=..., ...)` call | Matches the global rule: root config loaded in `main`, never inside builders/services |
| Alternate config profile via a second, higher-precedence yaml source | `cli/main.py::_parse_config_override` pre-parses a `--config PATH` flag out of `argv` (before `IngestorConfig`/the config-driven parser exist); `main()` calls `IngestorConfig.load(config_override)`. `IngestorConfig.load` (`configs/ingestor_config.py`) dynamically subclasses (`type(cls.__name__, (cls,), {"_config_override_file": config_override})`) when an override is given, so `_config_override_file` (a `ClassVar[Path \| None]`) carries the override path without any process-global state. `settings_customise_sources` reads that `ClassVar` via `getattr(settings_cls, ...)` and, if set, inserts `YamlConfigSettingsSource(settings_cls, yaml_file=config_override)` into the returned tuple, between `env`/`.env` and the always-present base-yaml source (ADR 0006) | The override yaml becomes a genuine, independent pydantic-settings source — reusing `YamlConfigSettingsSource` itself, not a dict we read and pass through `init_settings` — so `init_settings` stays reserved for real constructor kwargs (e.g. `postgres=...` in tests). `init_settings` (highest precedence) and `env`/`.env` still win over both yaml sources, so secrets are unaffected by which profile is active. Deep-merge across sources is pydantic-settings' own behavior — confirmed empirically for both a nested `BaseModel` field (`postgres`) and a plain `dict[str, str]` field (`layers`, replaced wholesale). So the override yaml only needs to list the fields that actually differ from the base yaml (`configs/ingestor_config.test-data.yaml` lists just `layers`/`quiz_images_dir`), not a full duplicate of every field — no drift risk on the fields it doesn't mention |
| `OpenRouterProvider` built lazily, only for the command that needs it | `cli/wiring.py:build_open_router_provider` builds `OpenRouterProvider(api_key=config.open_router_config.api_key.get_secret_value())`, called from `cli/main.py` only in the `prepare` branch, and passed into `run_prepare`/`dispatch_prepare` → `build_knowledge_enrichment_flow`/`build_quiz_enrichment_flow` (`open_router_provider: OpenRouterProvider`, required, no default) → each agent's `from_yaml(..., provider, ...)` → `BaseAgent.__init__`, which wraps `OpenRouterModel(model_name, provider=provider)`. `build_*_cleaning_flow`/`build_*_indexing_flow` never take the param — they call no agent | Dependency injection over global state: `pydantic_ai.providers.openrouter.OpenRouterProvider` would otherwise silently read `OPENROUTER_API_KEY` from `os.environ` itself; routing the key through `IngestorConfig.open_router_config` (`commons.configs.OpenRouterConfig`, a `BaseSettings` with `env_prefix="OPENROUTER_"`, built via `Field(default_factory=OpenRouterConfig)` so the env read happens at `IngestorConfig()` construction, not at module-import time) keeps the single root config as the one place secrets are read from. Building it lazily (not eagerly for every command) means `reset`/`status` run without `OPENROUTER_API_KEY` set |
| `AgentConfig.name` optional, agent identity inherited from config | `commons/ai/agents/configs/agent_config.py` — `name: str \| None = Field(default=None, ...)`; `BaseAgent.__init__` still does `self._name = config.name if config.name is not None else type(self).__name__`. Production YAML files under `configs/agents/` set an explicit `name:` (e.g. `road-sign-describer`); tests that omit it fall back to the concrete subclass name | Keeps a human-readable `LlmCallLogEntity.caller` configurable per-agent-instance in YAML without a separate constructor override — `from_yaml`'s `name` positional arg is only the YAML filename, never the identity |

| Degrade-gracefully exception to fail-explicit | `commons/ai/observability/services/queued_llm_call_tracker.py::_persist` catches bare `Exception` around `repository.insert`, logs `logger.warning(..., exc_info=True)`, and continues; `cli/commands/prepare.py:run_prepare` catches `psycopg.Error` around `wiring.build_postgres_client(...)` and dispatches with `tracker=None` | Observability must never break the main ingestion flow — a documented, narrow exception to "never swallow exceptions" (`.claude/rules/python/standards.md`) |
| Private `protocols/` nested inside `services/` for a narrow dependency | `commons/ai/observability/services/protocols/` — `_LlmCallLogRepository` `Protocol`, typing `QueuedLlmCallTracker`'s ctor param, satisfied structurally by both the real `LlmCallLogRepository` and test doubles with no common base class. Used to hold a second protocol, `_CostCalculator` (for the now-removed `LlmCostCalculator` — see `adr/0004-openrouter-native-cost-tracking.md`); the pattern (private structural protocol per narrow ctor dependency) still applies whenever `QueuedLlmCallTracker` or a sibling gains another swappable collaborator | Lets `QueuedLlmCallTracker.__init__` accept fakes in tests without nominal inheritance, same ISP rationale as `StoreRepository`/`FileRepository` protocols elsewhere — while keeping the package's public surface limited to ports something outside the package actually depends on |
| DTO + object-to-object mapper (`models/` + `mappers/`) | `commons/ai/observability/models/llm_call_capture_model.py` (`LlmCallCaptureModel`, a pydantic `BaseModel` holding one call's captured fields) and `mappers/llm_call_log_mapper.py` (`LlmCallLogMapper.from_model_to_entity(data: LlmCallCaptureModel) -> LlmCallLogEntity`, a real object-to-object transform, not a field-projection helper); `PydanticAILlmCallCapture` builds the DTO internally (`_to_capture_data`) and its `log` property just calls the mapper | Concrete application of the existing "intermediate model + mapper, never extra fields on the entity" rule (`.claude/rules/code-conventions.md`, entities section). | `@classmethod @contextmanager` factory composing capture + tracker | `pydantic_ai_llm_call_capture.py::PydanticAILlmCallCapture.tracked(caller, model, prompt, system_prompt, tracker)` — builds a fresh capture, yields it, tracks `capture.log` in `finally` | The `try: with capture: ... finally: tracker.track(...)` shape was pure boilerplate, not agent-call logic, and `BaseAgent` shouldn't own it — `tracked` lives next to the class it composes. **Naming discrepancy** (worth knowing, not "wrong"): the global
architecture rule (`~/.claude/rules/python/architecture.md`) calls for
`*Pipeline`/`*PipelineBuilder` classes in `orchestrators/`. In this repo,
`orchestrators/knowledge_flows.py` and `quiz_flows.py` instead use
**factory functions** returning a `flowstep.Flow`
(`build_knowledge_indexing_flow`, `build_quiz_cleaning_flow`, etc.) — the
`flowstep` framework's own vocabulary (`Flow`/`FlowBuilder`) replaces the
`*Pipeline`/`*PipelineBuilder` naming here. Follow this file's precedent
in `orchestrators/`, not the generic rule's literal class names.

`MapStep`, `EnrichDataStep`, and `EnricherProtocol` were removed from the
codebase (per the legacy architecture docs) — confirmed gone from `src/`.
Stale references to them survive only as outdated comments in
`orchestrators/context_keys.py`; don't use them as a model for new code.

  `commons/utils/pydantic_utils/` (`PydanticInstanceUtils.group_by`/`filter_by`,
  `PydanticModelUtils.validate_model_attributes`) — a generic "group/filter a

  validated multi-attribute key and non-hashable-value support via
  `HashUtils.make_hashable`. Fully tested (`tests/commons/utils/`), but **no

  multi-attribute or non-hashable-value grouping; don't add a second,
  parallel grouping helper.

## Naming conventions

- Suffix-per-role: `*Step` (flowstep steps), `*Service`/`*Enricher`
  (domain logic), `*Repository`, `*Client`, `*Mapper`, `*Agent`, `*Config`,
  `*Entity` (persisted rows under `domain/entities/`, e.g. `ArticleEntity`,
  `QuizQuestionEntity` — rule in `.claude/rules/code-conventions.md`).
- Flow factory functions: `build_<domain>_<stage>_flow` (e.g.
  `build_knowledge_indexing_flow`, `build_quiz_cleaning_flow`).
- `UseCase`-implementing collaborators are stored on `self` named after
  what they *are* (e.g. `self._agent`), never `self._use_case` — see
  `feedback_usecase_naming` memory.
