# ADR 0010: Migration Scripts Alongside init.sql

## Status

Proposed

## Context

Until now the project had exactly one schema mechanism: `db/init.sql`, mounted
into the Postgres container's `/docker-entrypoint-initdb.d/` and executed only
when the data directory is empty. Because it can never alter an existing
database, every schema change meant tearing down the container, wiping
`docker/.volumes/postgres_data`, and re-ingesting from scratch.

That workflow was affordable while the corpus was cheap to rebuild. It is no
longer neutral: the database now holds 3650 comma vectors and 7098 quiz vectors,
all of them paid for in embedding calls, and a wipe discards every one of them
regardless of whether the change touches them. Spec 0008 changes only the quiz
side, yet under the old workflow it would have forced the entire corpus to be
re-embedded.

There is a second, sharper cost. Spec 0007 establishes a retrieval baseline
measured against the current single-vector configuration. A wipe destroys that
configuration in place, which is why spec 0008 originally carried an ordering
constraint requiring the baseline to be captured and committed *before* the
schema change could proceed. A schema mechanism that forces experiments to be
sequenced around it is shaping the work rather than serving it.

## Decision

Schema changes to an existing database are applied by idempotent, transactional
SQL scripts under `db/migrations/`, named `NNNN_<slug>.sql` after the spec that
introduces them. `db/init.sql` is kept as the definition of the target schema for
freshly created volumes, and is updated in the **same change** as the migration.

Migration scripts must be:

- **idempotent** — `IF EXISTS` / `IF NOT EXISTS`, and guarded `DO $$` blocks where
  a plain clause cannot express the condition, so a re-run is a no-op rather than
  an error;
- **transactional** — a single `BEGIN`/`COMMIT`, so a failure leaves the schema
  untouched instead of half-applied;
- **data-preserving before destructive** — any step that moves data runs before
  the step that drops its source. `db/migrations/0008_quiz_query_representations.sql`
  moves `quiz_questions.embedding` into the new variant table before dropping the
  column;
- **shipped with an equivalence check** — an `information_schema` query to be run
  against both a migrated and a freshly initialised database and diffed.

No migration tool is introduced. Alembic remains rejected.

## Alternatives considered

- **Keep wipe-and-re-ingest as the only mechanism**: one mechanism, no drift
  possible, and the schema is always exactly what `init.sql` says. Rejected
  because it discards paid-for embeddings on every change, re-embeds data the
  change does not touch, and destroys in-place measurement baselines — forcing
  unrelated work to be sequenced around schema edits.
- **Adopt Alembic**: solves drift properly, with real versioning and autogenerated
  downgrades. Rejected as disproportionate: it adds a dependency, a migration
  environment, and a revision graph to a project whose schema is six tables and
  which deliberately avoids ORM machinery (psycopg direct, no SQLAlchemy). The
  cost/benefit may invert once the FastAPI app ships and the schema is live in
  more than one environment — revisit then.
- **Replace `init.sql` with a migration chain** (fresh databases replay every
  migration): removes the two-mechanism problem entirely, since there is only one
  path. Rejected because replaying an ever-growing chain to create an empty
  database is slower and harder to read than one declarative file, and the value
  of `init.sql` as a single legible statement of the current schema is high while
  the schema is small.

## Consequences

**Easier**: schema changes no longer cost the corpus. Spec 0008 became a migration
that preserves the 3650 comma vectors untouched and carries the 7098 quiz vectors
forward into the new table, so the only embedding spend is for genuinely new
representations. The ordering constraint that spec 0008 imposed on spec 0007
dissolved as a direct result.

**Harder — and this is the debt being accepted knowingly**: there are now two
schema mechanisms and nothing but discipline keeping them in agreement. A
migrated database and a freshly created one can silently diverge, and the failure
is quiet: everything works until someone recreates a volume and gets a different
schema. The equivalence check exists precisely because this cannot be prevented
structurally without a migration tool, only detected. Reviewers should treat a
migration that arrives without a matching `init.sql` edit as incomplete.

**Also harder**: migrations are irreversible by default. Each script carries a
commented rollback, but rollbacks are written by hand and are not exercised;
they are documentation of intent, not a tested path.
