# ADR 0041: Generate supplementary glossary candidates live, merge with DB priority, keep them ephemeral

## Status

Proposed

## Context

`glossary_entries` (spec 0019, ADR 0038) is a precomputed, offline-built table:
`build-glossary` extracts term/definition pairs from the parsed corpus, verbatim,
under an `output_validator` that rejects any definition not present in the source
text. Coverage is necessarily incomplete at any point in time — a quiz question can
reference a technical term the offline pass hasn't reached yet, or never will (the
corpus doesn't cover every word a candidate might not know). Before spec 0021,
`ExplanationService._vocabulary_outcome` (ADR 0035) only ever read this table via
`GlossaryReadRepository.candidates_for`; a term missing from it simply never appeared
in `translation_hints`, with no path to close that gap short of a full corpus-glossary
rebuild.

## Decision

`ExplanationService._vocabulary_outcome` now gathers a second, independent source
alongside the DB read: `GlossaryEnricherAgent`, an answer-blind agent that generates
term/definition candidates live, on every `GET .../explanation` call, grounded on the
same live-retrieval stack `CommaSelectorService` already uses for comma labeling
(`LiveLabelingStackProvider.quiz.find_with_vector` → `candidate_set`), falling back to
its own general knowledge when no retrieved comma covers a term (FR-3). The two
candidate lists are combined by a new pure function, `merge_glossary_candidates`: the
DB-retrieved list always wins a conflict (keyed on `term.strip().casefold()`, AD-6), an
on-demand candidate is kept only when its normalized term doesn't already match a DB
one. On-demand candidates are never persisted — `glossary_entries` is untouched by this
stage; every request re-generates them fresh. A new `GlossaryTermOrigin` field
(`VERBATIM_CORPUS` / `AGENT_GENERATED`) on `CitedGlossaryTerm`/`CitedGlossaryTermResponse`
tells the client which source grounded each cited term.

## Alternatives considered

- **Offline gap detection + scheduled batch fill**: periodically scan quiz questions
  for terms missing from `glossary_entries` and fill them via a batch job, the same
  shape as `build-glossary` itself. Rejected — needs a detection heuristic (what
  counts as a "missing term" worth filling?) and a scheduling story, and leaves a
  window between a gap appearing and it being filled during which the question is
  still unanswered. The live-generation approach answers every request immediately,
  with no detection step and no window.
- **Generate live, but write through into `glossary_entries`** so a term generated
  once is cached for every future request. Rejected — `glossary_entries` has a
  verbatim-extraction contract (ADR 0038): every row is guaranteed to be extracted,
  not generated, from the corpus text, enforced by `GlossaryExtractorAgent`'s
  fidelity check. `GlossaryEnricherAgent` explicitly does *not* have that guarantee —
  it falls back to general knowledge when the corpus doesn't cover a term (FR-3).
  Writing its output into the same table and column would silently mix two different
  provenance/quality guarantees with no schema-level way to tell them apart after the
  fact — a future reader of `glossary_entries` could not tell a verbatim row from a
  generated one without an extra column, which is exactly the `origin` field this
  decision instead puts on the *response* DTOs, where it's cheap and never touches the
  corpus table's contract at all.

## Consequences

A question about a term the offline corpus pass hasn't reached gets a real answer on
every request, immediately, with no dependency on a scheduled job or a detection
heuristic — and the corpus glossary itself is unaffected, so it can only be
grown/improved through the existing, audited `build-glossary` pipeline, never silently
mutated by live traffic.

The cost, knowingly accepted: the same term is regenerated by the LLM on every request
that cites it — there is no cross-request cache for on-demand candidates, so a
frequently-asked term pays its generation cost (latency, tokens) again each time. Usage
patterns never feed back into `glossary_entries`'s own coverage; closing a real gap
still requires a human-triggered `build-glossary` rerun (or corpus edit) — this
decision does not reduce that need, it only covers the gap's user-facing symptom
per-request. If cross-request caching or usage-driven glossary growth becomes a real
product need later, that is a new, separate decision, not implied by this one.
