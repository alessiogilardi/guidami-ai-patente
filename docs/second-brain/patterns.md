# Patterns and Conventions

Enforceable rules (typing, DI ordering, config-loading, import style) live
in `~/.claude/rules/python/` and `.claude/rules/`. This file only records
recurring idioms actually adopted in the code, as a reference for reuse —
it does not restate those rules.

## Adopted patterns

| Pattern | Where it's used | Why |
|---|---|---|
| `UseCase[T_In, T_Out]` / `AsyncUseCase` protocol | `src/commons/use_cases/use_case.py` — `__call__` is `@final`, delegates to abstract `execute()` | Uniform callable contract for domain logic; every business-logic unit is typed, testable, composable |
| `ForEach[T, U]` | `src/commons/use_cases/for_each.py` — a `UseCase[Iterable[T], list[U]]` wrapping a per-item callable | Turns any `UseCase`/callable into a list-mapper without per-step loop boilerplate |
| `FlatMap[T, U]` | `src/commons/use_cases/flat_map.py` — a `UseCase[Iterable[T], list[U]]` wrapping a per-item `Callable[[T], Iterable[U]]`, concatenating results | One-to-many transforms (one input produces N outputs); e.g. `ApplyStep("expand_to_embeddable_commas", FlatMap(ArticleMapper.from_cleaned_to_embeddable_commas), ...)` in `orchestrators/knowledge_flows.py` (a plain `@staticmethod` reference works directly, no callable-instance wrapper needed — `FlatMap.__init__` only requires `Callable[[T], Iterable[U]]`) and `ApplyStep("flatten_quiz", FlatMap(QuizMapper.from_parsed_to_cleaned_all), DeduplicateQuizItemsService(), ...)` in `orchestrators/quiz_flows.py`. A third shape, zero-or-one rather than one-to-many: `ApplyStep("map_to_quiz_images", FlatMap(QuizMapper.from_embedded_to_quiz_images), ...)` (spec 0008 Phase 1) returns `[QuizImageEntity]` when the question has an image, `[]` otherwise — `FlatMap` needs no dedicated zero-or-one variant, since a `Callable[[T], Iterable[U]]` already covers the empty-list case for free |
| `ApplyStep(ForEach(...))` composition | `orchestrators/knowledge_flows.py` — e.g. `ApplyStep("map_to_chunk_entity", ForEach(ArticleMapper.from_embeddable_chunk_to_knowledge_chunk), ...)` | Standard glue between the domain-agnostic `flowstep` framework (external git dependency, see `docs/second-brain/architecture.md`) and per-item domain transforms/mappers |
| `AsyncApplyStep` | `flowstep.steps` (external git dependency, same package as `ApplyStep`) — used in `orchestrators/quiz_flows.py::build_quiz_enrichment_flow` for the LLM-enrichment step (knowledge-corpus enrichment used it too, until spec 0001/T-13 removed that flow entirely) | Fully generic (owns one `asyncio.run`, no repo-specific coupling), so it belongs upstream per the `flowstep`-vs-local split documented in `docs/second-brain/layout.md`; no local copy is kept |
| `Iterable[T]`-typed `ApplyStep` transforms | All `UseCase` subclasses passed as `ApplyStep(...)` transforms (`ForEach`, `FlatMap`, `DeduplicateQuizItemsService`, `EmbedQuizMetadata`, `ImageDescriptionEnricherService`, `NormReferenceEnricherService`) declare `execute(self, request: Iterable[T]) -> list[U]` | `flowstep`'s `ApplyStep` (external dependency) types transforms as `Callable[[Iterable[Any]], Iterable[Any]]`; a `list[T]`-only parameter fails pyright. Transforms that traverse `request` more than once materialize it first (`request = list(request)`) since `Iterable` doesn't guarantee re-iterability |
| Dedup-before-LLM enricher via `deduplicate` | `services/quiz/enrichers/norm_reference_enricher.py` — build a `dict[key, response]` by mapping `commons.utils.deduplicate(items, key=_make_key)` through the agent, then broadcast each response to every row sharing the key | One LLM call per unique key instead of per row; the order-preserving `deduplicate` pass replaces manual `seen`-set bookkeeping |
| Group-by-resource enricher with concurrent LLM calls | `services/quiz/enrichers/image_description_enricher.py` — `_group_by_image` (sync `defaultdict(list)`, keyed on the image filename only) → `_fetch_descriptions` (async: builds every `RoadSignDescriberRequest` first via `RoadSignDescriberMapper.from_enriched_quizzes_to_request` — one per image, concatenating every quiz's context — then fires `_describe_image` calls with `asyncio.gather` under an `asyncio.Semaphore(max_concurrency)` created per run) → `_enrich_quiz` (sync, broadcasts each response to every quiz sharing that image). `execute` stays sync and drives the async part with `asyncio.run(...)` | One vision call per **image**, not per `(image, topic, text)` triple — the describer is answer-blind and already treats quiz text as weak context, so per-triple specialization only bought divergent/costlier calls. The semaphore is built fresh per `_fetch_descriptions` call (never stored on `self`) because an `asyncio.Semaphore` binds to the event loop of its first use, and `execute`'s `asyncio.run` spins a fresh loop every call — storing it would break re-use across runs. Per-image failures degrade (`None`, logged) without aborting the batch |
| Declarative embedding-text spec, injected inline (`EmbedCommasStep`) | `orchestrators/knowledge_flows.py` — title + comma text, one part per line, discarding empty parts (`FieldSpec(extractor=lambda comma: comma.article_title or None)` / same for `text`, `or None` turning a falsy value into a droppable field), no context since AD-18 removed LLM enrichment; `EmbeddingSpec(fields=[...], separator="\n", normalize_whitespace=False)` reproduces the exact join the former `embedded_text` computed property did — that property is **deleted** from `EmbeddableArticleComma` entirely, since the text is now composed declaratively from fields the model already has, with no need for a dedicated field of its own. `FieldSpecComposer[EmbeddableArticleComma](EmbeddingSpec(...))` is built inline at the `ModelEmbeddingService[EmbeddableArticleComma]` call site and injected directly — no adapter class: `FieldSpecComposer.compose(model) -> str` (see the composers row above) already satisfies `TextComposer[T]` on its own, since `compose` and the `str | None`-returning `compose_or_none` are two separate methods on the same class, not one overloaded signature. The quiz side never had a single-property pattern to begin with: one question needs several different texts (one per variant) — see the registry row below | Removes a model field whose only job was mirroring two other fields into one derived string — the composition is declared once, next to its only consumer, using the same declarative primitives as the quiz registry, instead of duplicating join logic as a property; splitting `compose`/`compose_or_none` into two methods (rather than one method returning `str \| None` always) means the 1:1 case never pays an Optional-handling tax it doesn't need |
| `TextComposer[T]`/`OptionalTextComposer[T]` protocols + declarative/template/callable composers | `commons/ai/embedding/protocols/text_composer.py::TextComposer[T]` (`compose(model: T) -> str`, structural — the 1:1 case, always a string) and `protocols/optional_text_composer.py::OptionalTextComposer[T]` (`compose_or_none(model: T) -> str \| None`, structural — for representations that may legitimately be absent, e.g. one variant among several for a quiz question; a distinct method name rather than an overload of `compose`, so one class can satisfy both protocols at once). Three composer implementations in `composition/`: `FieldSpecComposer[T]` (declarative `EmbeddingSpec`/`FieldSpec` recipe — extract, then render, then join/normalize as four small utility methods rather than one nested loop, see `models/{field_spec,embedding_spec}.py`; implements **both** `TextComposer[T]` (`compose`, unconditionally a string) and `OptionalTextComposer[T]` (`compose_or_none`, returns `None` when a field marked `skip_if_none=False` — "required" — is missing, rather than a partial/garbage text; the check is unconditional, no separate spec-level flag), `TemplateComposer[T]` (`string.Template` `$var` substitution, `BaseModel`/dataclass/`Mapping` dispatch ported from `agents/utils/prompt_renderer.py::PromptRenderer`, but strict `.substitute()` not `.safe_substitute()` — an unresolved placeholder must raise, not get embedded literally into the text sent for embedding; implements `TextComposer[T]`, always returns `str`), `CallableComposer[T]` (wraps any `Callable[[T], str]`, e.g. `operator.attrgetter("embedded_text")` for a model that already has its own text-building property, avoiding a throwaway composer class; implements `TextComposer[T]`). `commons.ai.embedding.services.ModelEmbeddingService[T]` composes+embeds a batch of models 1:1 (`composer: TextComposer[T]`, `embedding_service: EmbeddingService`), returning `EmbeddingResult[T]` (`model`/`text`/`embedding`) — it delegates all chunking/progress to the injected `EmbeddingService` rather than duplicating it | Separates "how to turn a model into text" (swappable, per-model-type) from "how to batch-embed text" (`EmbeddingService`, unchanged); two differently-named methods on `FieldSpecComposer`, rather than one `compose` returning `str \| None` always, keep `ModelEmbeddingService[T]`'s 1:1 pipeline (`EmbeddingResult.text: str`, not Optional) from ever having to handle a missing text — a caller injecting `FieldSpecComposer` there uses `.compose()`, one injecting it into `QuizVariantSpec` (see the registry row below) uses `.compose_or_none()`, no wrapper needed either way; an accidental composer/model-type or `str`/`Optional[str]` mismatch at a call site is a type error, not a runtime bug |
| Registry of named text-composers + dedup key (`QuizVariantSpec`/`QUIZ_VARIANT_REGISTRY`) | `services/quiz/quiz_variant_spec.py` + `services/quiz/quiz_variant_registry.py` (spec 0008 Phase 2, AD-7/AD-8; ADR 0014 proposed generalizing the dedup/omission/fan-out mechanics into `commons/ai/embedding/` as a `VariantSpec[T]`/`VariantModelEmbeddingService[T]` pair — rejected, see `docs/second-brain/adr/0014-embedding-composition-layer.md`) — a `Mapping[str, QuizVariantSpec]` pairing a variant `name` with a `text_composer: commons.ai.embedding.OptionalTextComposer[EmbeddedQuizModel]` (`compose_or_none(item) -> str \| None`; `None`, never a stored null vector, when the item lacks that variant's input) and a `dedup_key: EmbeddedQuizModel -> str` (defaults to `item.number` — a domain-sensible default, since `QuizVariantSpec` is concrete to `EmbeddedQuizModel`, not generic; overridden only for `image_description`, `item.image_filename or item.number`, so several questions sharing one image issue one embedding call, broadcast back — AD-8). Every `text_composer` in the registry is a plain `FieldSpecComposer` wrapping a declarative `EmbeddingSpec`/`FieldSpec` recipe — no hand-written text-joining functions: fields that are simply optional use `FieldSpec`'s default `skip_if_none=True` (silently dropped when absent, e.g. `image_description` in the `topic_text` variant); fields whose absence should invalidate the *entire* variant (e.g. `quiz_metadata.vector_search_queries` for `search_queries`/`combined`/`combined_description`) are marked `skip_if_none=False`, which `compose_or_none()` treats as "required" and returns `None` outright if missing. `EmbedQuizVariantsService` resolves `IngestorConfig.quiz_embedding_variants` (names only) against the registry (code) at construction time, raising `KeyError` on an unknown name — a startup error, not a silently missing arm — then itself performs the dedup/omission/fan-out mechanics (build every item's text via `text_composer.compose_or_none`, group by `dedup_key`, embed one text per group via the injected `EmbeddingService`'s `__call__`, fan the vector back out) and remaps the rows onto the persisted `EmbeddableQuizVariant` DTO | Splits "which representations are enabled" (config, changes without a code edit) from "what a representation actually is" (code, since text composition is a function, not a YAML value) — adding a seventh variant is one registry entry + one config name, no schema change and no change to the write path or the evaluation harness's arm enumeration (which reads variant names back from the database, never from this registry); the dedup/fan-out mechanics were deliberately **not** generalized into `commons/` (ADR 0014, rejected) — the quiz registry is the only caller, so a fourth `commons/ai/embedding` subpackage for one consumer wasn't judged worth it; the declarative composition (`EmbeddingSpec`/`FieldSpec`) is reused instead, which is the part that actually generalizes |

Only once the DB has authorized the name does it call `guidami_ai_patente/repositories/quiz_image_repository.py::QuizImageRepository.read(filename) -> bytes`, a `@repository` (not a `@client` provider — same "no caller wants the client itself, they want bytes" reasoning as `AgentConfigRepository`, AD-16) wrapping `commons.clients.file_system.LocalFileSystemClient(config.quiz_images_dir)`; that client's `_get_safe_read_path` is the second, structural boundary — it anchors every read to `quiz_images_dir` and raises `PermissionError` on anything resolving outside it, so even a malformed name that somehow reached the database cannot address a byte elsewhere. Both `FileNotFoundError` (row absent from disk) and `PermissionError` (row resolves outside the directory — should never happen given layer one, but not assumed) collapse to the same `QuizImageNotFoundError` in the service, deliberately not a distinct 403: telling a caller its traversal was *recognised* is more than a 404 needs to reveal. `QuizImage(BaseModel, frozen=True)` (`models/quiz_image.py`, `content: bytes`, `media_type: str`) is the returned DTO; `media_type` comes from `mimetypes.guess_type(filename)`, defaulting to `application/octet-stream` on an unrecognised suffix. Integration-tested against the real committed `data/quiz-images/` directory (`tests/guidami_ai_patente/services/test_quiz_image_service.py`), including five traversal payloads (`../../.env`, `../.env`, `sub/dir.png`, `..\\..\\.env`, `""`) that must all fail the DB lookup, never reach `LocalFileSystemClient` | Security-relevant: the order of the two checks *is* the guarantee, not an implementation detail — swapping the DB check to happen after the read would turn the anchored file-system client into the API's only line of defense, when the actual requirement (FR-12) is that the endpoint serves *exactly* the images the database names. Splitting into repository + service (rather than one class doing both) keeps the DB authorization testable/reasoned-about independently of the filesystem boundary, and keeps `commons/` infrastructure (`LocalFileSystemClient`) an implementation detail behind `QuizImageRepository`, never imported directly by the service |
| Literal-before-parameterised route declaration order (spec 0012, quiz-flow-api-phase2 plan Task 13) | `guidami_ai_patente/api/routers/quiz_questions.py` — `GET /quiz-questions/topics` and `GET /quiz-questions/random` are both declared, in that order, before `GET /quiz-questions/{number}` in the same `APIRouter`. Every route handler across both new routers (`quiz_questions.py`, `quiz_images.py`) is `async def`, reaching its synchronous service/mapper call through exactly one `await asyncio.to_thread(...)` call and containing no `try`/`except` and no HTTP status logic of its own — domain exceptions propagate to the global handlers `register_exception_handlers` already wires (Task 4/AD-17) | FastAPI dispatches a path against its router's routes **in declaration order** and stops at the first match — a `{number}` path parameter matches the literal string `"topics"` just as readily as a real question number, so declaring the parameterised route first would silently 404 the topics menu (interpreted as an unknown question) instead of ever reaching the intended handler. This is a structural router-authoring rule, not a one-off fix: any future literal path under `/quiz-questions/` (or any other prefix mixing literal and `{param}` routes) must be declared before the parameterised sibling it would otherwise be shadowed by. The `async def` + single `asyncio.to_thread` shape keeps the sync-only service/repository/mapper stack (AD-25) off the event loop without needing an async rewrite of any lower layer |

**Naming discrepancy** (worth knowing, not "wrong"): the global
architecture rule (`~/.claude/rules/python/architecture.md`) calls for
`*Pipeline`/`*PipelineBuilder` classes in `orchestrators/`. In this repo,
`orchestrators/knowledge_flows.py` and `quiz_flows.py` instead use
**factory functions** returning a `flowstep.Flow`
(`build_knowledge_indexing_flow`, `build_quiz_cleaning_flow`, etc.) — the
`flowstep` framework's own vocabulary (`Flow`/`FlowBuilder`) replaces the
`*Pipeline`/`*PipelineBuilder` naming here. Follow this file's precedent
in `orchestrators/`, not the generic rule's literal class names.

codebase (per the legacy architecture docs) — confirmed gone from `src/`.
Stale references to them survive only as outdated comments in
`orchestrators/context_keys.py`; don't use them as a model for new code.
